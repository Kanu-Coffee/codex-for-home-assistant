## 2. 현재 구현의 미수용 사항

- `codex-runtime-manager.mjs:1193` 부근은 `loadedThreads.length > 0`만으로 busy를 반환한다. 이는 작업이 없는데도 업데이트를 중지시키는 조건이다.
- 같은 파일 `applyUpdate()`의 `liveAllowed = false`는 실제 유휴 판정 뒤에도 모든 관리형 서버의 전환을 막는다. 기존 스케줄은 정상이어도 적용에 도달하지 못한다.
- relay는 미저장 thread의 복원 가능성을 작업 busy와 혼용한다. 특히 아직 내용이 없는 thread의 rollout 부재는 진행 작업의 증거가 아니다.
- CLI/TUI의 프로세스 생존만으로 작업 활성 여부를 대체하는 경로도 남아 있다.

FIX_08의 허위 recovery 성공·journal 삭제와 임의 boolean 우회를 막은 보완은 인정한다. 그러나 blanket 차단을 유지한 것으로 이번 기능을 완료할 수는 없다.

## 3. Executor 구현 지시

1. **기존 운영 스케줄 유지:** 하루 4회 check/stage 및 pending 재검사→`applyUpdate()` 흐름을 재사용한다. 새로운 스케줄러나 UI 감지 기능을 만들지 않는다.
2. **보류 조건을 실제 작업으로 한정:** 수락된 in-flight 요청, queued 요청, 진행 turn/tool/child 작업, 승인/입력 응답 대기와 실제 background 작업은 보류한다. 프로세스·연결·로드된 대화·화면 열림 자체는 활성 작업으로 계수하지 않는다. 관측 오류는 실제 오류로 표시하되 모든 정상 유휴 연결을 영구 unknown으로 분류하지 않는다.
3. **유휴이면 기존 backend 업데이트·재시작:** 실제 유휴 검사와 admission을 연결해 기존 적용 단계에 진입하게 한다. loaded thread 검사를 지우거나 false gate만 해제한 채 기존 파괴적 경합을 방치하지 않는다. 시작 직전 수락된 작업은 old에서 정상 처리하고, 전환 중 새 입력은 준비된 backend에 정확히 한 번 전달한다.
4. **유휴 대화의 재연결 처리:** 지원되는 frontend 재연결·저장된 thread 재로드를 구현한다. 내용 없는 대화의 미저장 rollout이나 UI 메모리 상태 완벽 이관을 정상 업데이트의 선행 조건으로 삼지 않는다. 대화 기록은 유지하고 다음 사용자 요청이 정상 처리되는지 검증한다. 단순 frontend 프로세스 생존을 성공 증거로 쓰지 않는다. 기존 연결 유지와 사용자 사용성은 구현하되 ‘빈 thread를 같은 메모리 상태로 복원 못한다’는 이유로 영구 보류하지 않는다.
5. **복구는 실제 실행 범위에 맞게:** 기존 no-session 적용의 검증된 복구를 재사용하고 backend 교체에 추가되는 실패만 다룬다. journal을 복구 없이 삭제하거나 미완료 상태를 성공으로 보고하지 않는다. 모든 미래 버전의 범용 migration을 완성하는 일을 현재 정상 경로의 무기한 선행 과제로 만들지 않는다.
6. 사용자·개발 문서의 idle/active 정의를 위 기준에 맞춰 정정한다. 실제 구현 뒤 `FIX_09_REPORT.md`를 작성한다. 이전 미완료가 새 요구 충족으로 소급되는 것은 아니다.

## 4. 수용 시험

- CLI/TUI 또는 Remote 연결을 유지하고 아무 요청도 보내지 않는다. 자동 스케줄/재검사에서 기존 backend가 새 버전으로 바뀌고 다음 요청이 정상 처리되어야 한다.
- 저장된 대화를 열어 둔 경우와 내용 없는 새 대화를 열어 둔 경우 모두, 열림 자체가 보류 이유가 되어서는 안 된다.
- 진행 요청·queued·tool/approval/background 작업은 보류하고 종료 뒤 다음 허용 검사에서 적용한다.
- 검사/종료 사이 새 요청, 전환 중 입력, 후보 기동 실패·업데이트 프로세스 재시작에서 요청 유실·중복 및 허위 성공이 없어야 한다.
- 기존 ‘모든 세션 종료 후 업데이트’ 경로와 예산·cooldown·OFF/manual 동작을 유지한다.

위 정상 경로를 로컬 production 흐름에서 검증한 뒤 재리뷰한다. 더 처리할 correction이 없으면 사용자가 설치할 수 있는 새 dev 버전 배포를 지시하고 정확한 저장소·버전·시험 절차를 전달한다. 실기기 인수 자체를 dev 배포 전 완료한 것처럼 요구하거나 기록하지 않는다.
